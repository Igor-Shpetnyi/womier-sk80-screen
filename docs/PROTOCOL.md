# Протокол екрана Womier SK80 — реверс-інжиніринг

Документація формату, яким фірмовий Windows-драйвер (`Womier-SK80 Driver`, чіп **SONiX**,
композитний USB-пристрій `VID_05AC&PID_024F` — спуфить Apple vendor ID) заливає GIF-анімації
на вбудований TFT-екран клавіатури. Розкрито повністю: формат кадру, заголовок, USB/HID-транспорт
і командний handshake — достатньо, щоб надсилати довільний власний контент напряму, в обхід драйвера.

## Ідентифікація пристрою

```
VID:PID = 05AC:024F
```

USB-композит з 4 HID-інтерфейсами:

| Інтерфейс | Призначення                             | Ендпоінти                    |
|-----------|------------------------------------------|-------------------------------|
| MI_00     | Стандартна клавіатура (boot keyboard)     | 0x81 IN                       |
| MI_01     | Consumer control / system control         | 0x82 IN                       |
| **MI_02** | **Vendor-defined — канал даних екрана**   | **0x84 IN, 0x03 OUT**          |
| **MI_03** | **Vendor-defined — канал команд**         | feature reports, wIndex=3     |

⚠️ **Ніколи не чіпати MI_00/MI_01** — це реальна клавіатура, будь-який вплив на введення тексту
неприпустимий. Перед прямим HID-доступом обов'язково закрити офіційний драйвер повністю
(вікно + трей), інакше `hid.open_path()` кине `OSError: open failed`.

## Інструменти для власного дослідження

- **Wireshark + [USBPcap](https://desowin.org/usbpcap/)** для захоплення USB-трафіку (після
  встановлення USBPcap потрібне перезавантаження ПК).
- `tshark` для аналізу захоплень з командного рядка.
- Пряме надсилання HID: пакет [`hidapi`](https://pypi.org/project/hidapi/) (`pip install hidapi`,
  імпортується як `import hid`).

Корисні tshark-фільтри:

```bash
tshark -r capture.pcapng -Y "usb.idVendor" -T fields -e usb.device_address -e usb.idVendor -e usb.idProduct
tshark -r capture.pcapng -Y "usb.dst==1.<addr>.3" -T fields -e frame.number -e frame.len -e usbhid.data
tshark -r capture.pcapng -Y "frame.number==<n>" -V     # повний розбір пакета (control transfers)
```

**Важливо:** дані image-payload лежать у полі **`usbhid.data`**, НЕ в `usb.capdata`.

## Формат зображення

### Піксель

RGB565, little-endian. Приклад: чистий червоний `(255,0,0)` → значення `0xF800` → байти на
дроті `00 F8`.

```python
val = ((r >> 3) << 11) | ((g >> 2) << 5) | (b >> 3)
bytes_le = struct.pack('<H', val)
```

### Роздільна здатність контенту

**160 × 90, row-major.** Підтверджено точним побайтовим збігом (похибка 1.74/255 проти 57+/255
для будь-якого іншого варіанта) при порівнянні з наперед відомим тестовим зображенням
("лівий-червоний / правий-синій"), залитим через офіційний драйвер.

⚠️ Це **не** 240×135 — заявлена вендором роздільна здатність екрана. Драйвер сам масштабовує
вхідний GIF до 160×90 перед відправкою. Кілька інших гіпотез (240×64, 120×120, 30×480
column-major) були спростовані прямими тестами. Довіряти варто лише точному побайтовому
порівнянню з реальним трафіком, не візуальним здогадкам по фото екрана.

### Один кадр на дроті

```
30720 байт = 28 800 байт контенту (160×90×2) + 1920 байт padding (завжди 0x00)
```

### Заголовок передачі (1218 байт, іде перед усіма кадрами)

```
offset 0        : кількість кадрів (1 байт)               0x03=3, 0x0a=10, 0x3c=60
offset 1..N     : затримка кожного кадру (1 байт/кадр)     value*2 = мс, З ПЕРЕПОВНЕННЯМ mod 256!
offset N+1..10  : невикористані слоти = 0xFF (масив зарезервований мінімум на 10 слотів)
offset 11..1217 : незмінний блок (однаковий у всіх спостережених випадках)
```

**Формула затримки** (підтверджено на кількох точках, включно з переповненням):

```
delay_byte = (запитані_мс // 2) mod 256
```

| Запит (мс) | delay_byte | Реальна відтворена затримка |
|---|---|---|
| 100   | 50  (0x32) | 100 мс — коректно            |
| 500   | 250 (0xFA) | 500 мс — коректно            |
| 1000  | 244 (0xF4) | 244×2 = 488 мс (!) — переповнення |
| 10000 | 136 (0x88) | 136×2 = 272 мс (!) — переповнення |

**Максимальна реальна затримка на кадр — 510 мс (255×2).** Довші інтервали (наприклад "тік раз
на секунду") цим полем фізично не підтримуються — прошивка не має ширшого поля для затримки.

### Повний стрім

```
[HEADER 1218 байт]
[FRAME 0: 30720 байт]
[FRAME 1: 30720 байт]
...
[FRAME N-1: 30720 байт]
```

## USB/HID транспорт

### Дані зображення — endpoint 0x03 OUT, інтерфейс MI_02

- HID Output Report, рівно **4096 байт** корисного навантаження на кожен запис (+1 байт report ID
  попереду при відправці через `hid.write()`).
- Порції йдуть строго послідовно; заголовок передається один раз на початку всього стріму.
- **Обов'язкова затримка між порціями + читання IN-ендпоінта (0x84) як flow control** — інакше
  прошивка "захлинається":
  - 0 затримки, без читання IN → зависання клавіш.
  - 30 мс + читання IN → працює, але видимі глюки на екрані.
  - **70 мс + читання IN (`dev.read(64, timeout_ms=50)`) → стабільно, без глюків.** Поточне
    робоче значення в [`protocol.py`](../protocol.py).

### Команди — feature reports, інтерфейс MI_03 (wIndex=3)

Три команди, завжди в цій послідовності: **start → params → [дані на endpoint 0x03] → commit**.

```
START  (SET_REPORT, Feature): 04 18 00 00 00...00                       (завжди однаковий)
PARAMS (SET_REPORT, Feature): 04 72 [XX] 00 00 00 00 [CC CC] 00...00
                                       ^                ^^^^^
                                       |                total_chunks, little-endian uint16
                                       категорія/сегмент — не до кінця розгадано, див. нижче
COMMIT (SET_REPORT, Feature): 04 02 00 00 00...00                       (завжди однаковий)
```

Після кожного `SET_REPORT` драйвер також робить `GET_REPORT` (той самий wIndex=3) — схоже на
перевірку статусу/ack; не є критичним для роботи, але зроблено для точності відтворення трафіку.

**Байт `[XX]` у params не має виведеної формули.** Спостереження:

| Кількість кадрів | total_chunks | байт XX |
|---|---|---|
| 1 (офіційна функція "текст на фреймі") | 8   | `0x01` |
| 3                                      | 23  | `0x06` |
| 60                                     | 451 | `0x07` |

Практична рекомендація: **не вгадувати цей байт** — брати лише з реального captured прикладу
з такою ж кількістю кадрів. Саме тому в [`protocol.py`](../protocol.py) є фіксований реєстр
`_TEMPLATES`, а не спроба генерувати заголовок/params "з нуля" для довільної кількості кадрів.

## Небезпечні знахідки та чому вимкнено 1-кадровий режим

1. Надто швидка передача без flow control (0 затримки, без читання IN) → зависання клавіш.
2. `frame_count=1` з params-байтом, скопійованим з 3-кадрового випадку (`0x06` замість
   правильного `0x01`) → зависання клавіш.
3. `frame_count=1` навіть із **виправленим** params-байтом (`0x01`, що збігається з реальним
   captured прикладом офіційної функції "текст на фреймі") → **клавіші зависли знову.**

Причина нестабільності 1-кадрового режиму так і не з'ясована до кінця — ширша, ніж один байт.
**Висновок: `protocol.py` навмисно підтримує лише 3- і 10-кадрові шаблони**, підтверджені
реальним трафіком; будь-яка інша кількість кадрів викликає `ValueError` замість спроби
"вгадати" заголовок.

Кожна передача (навіть стабільна) вмикає на екрані анімацію "завантаження" і **вимикає
RGB-підсвітку всієї клавіатури** на час передачі (~3.5с для 3-кадрового шаблону при 70мс/порцію)
— спосіб обійти це не знайдено; спроба пропустити start/params не спрацювала (прошивка все
одно показує завантаження і повертає код помилки в commit).

**Якщо клавіші зависли** — просте перепідключення USB-кабелю відновлює нормальну роботу,
апаратних чи прошивкових пошкоджень це не спричиняло за весь час дослідження.

## Що лишилось нез'ясованим

1. Точна причина зависання в 1-кадровому режимі (padding-хвіст? порядок GET_REPORT? якийсь
   timing-нюанс?).
2. Формула байта `XX` у params для довільної кількості кадрів.
3. Спосіб уникнути "завантаження"/вимкнення підсвітки під час оновлення — схоже, у прошивці
   немає "легшого" шляху для часткового/швидкого оновлення, кожен апдейт — повний кадр.
4. Чи можливе часткове оновлення кадру (лише змінені пікселі) — ознак цього в спостереженому
   трафіку не було.

Якщо продовжуватимете це дослідження — саме ці чотири пункти найцінніше дослідити далі.
